# V4「状态机驱动」架构对 Customer-Agent 的借鉴分析

> **文档性质**：技术讨论稿，不涉及代码修改。  
> **对照对象**：某 AI 智能客服系统 V4 重构实践（SessionMemory + StateMachine + PromptBuilder + 按需 RAG + 零 Token 规则节点）。  
> **当前项目**：Customer-Agent（拼多多 AI 客服桌面端，Python + PyQt6 + Handler 链 + Agno + LanceDB）。

---

## 1. 结论摘要

Customer-Agent **已经具备 V4 思想的部分雏形**，但实现方式更偏「**Handler 责任链 + 轻量 TaskState**」，尚未形成统一的、可观测的全局状态机。

| V4 模块 | 当前项目对应 | 契合度 | 建议 |
|---------|-------------|--------|------|
| SessionMemory（intent/slots/stage） | `TaskState` + `chat_sessions.task_state_json` | ★★★☆☆ | 可升级，不必推倒重来 |
| StateMachine（规则流转） | 各 Handler 自带 `can_handle` + 改址/售后规则 | ★★☆☆☆ | **高价值**，建议分场景补全 |
| PromptBuilder（有上限拼接） | `build_layered_prompt` + 未回复合并 | ★★★★☆ | 继续收紧上限即可 |
| 按需向量检索 | Agno `search_knowledge=True`，几乎每轮 RAG | ★☆☆☆☆ | **最值得借鉴**，收益最大 |
| 零 Token 规则节点 | 关键词/改址/售后/转人工意图（正则） | ★★★★☆ | 已有，可扩展 slot 规则 |
| MCP 企业集成 | 拼多多 MMS API + 开放平台 + Agent Tools | ★★★☆☆ | 思路类似，非 MCP 协议 |

**一句话**：不必整体迁移成「汽车试驾销售 V4」，而应把 V4 的**按需 RAG、显式阶段、槽位驱动**嫁接到现有 Handler 链上——这与拼多多电商场景（改址、售后、物流、商品咨询）天然匹配。

---

## 2. 当前项目架构速览

```
买家消息 (WebSocket)
    ↓
消息队列 + Consumer（per-buyer 锁）
    ↓
Handler 责任链（按顺序，命中即返回）
    AddressChange → OrderLogistics → ImageVideo → AfterSales
    → BuyerEmotion → Keyword → AIReply → CatchAll
    ↓
AI 路径：未回复合并 → build_layered_prompt → Agno Agent
         → knowledge_retriever(RAG) → LLM → 出站发送
```

**已有结构化能力：**

- **`TaskState`**（`conversation_memory.py`）：`intent`、`slots`、`pending_confirm`、`flow_node`
- **三层记忆**：短期原文 / 任务状态 / 长期摘要（规则摘要，非向量）
- **业务 Handler**：改址（`address_parse` 正则抽槽）、售后（`after_sales_policy` 意图枚举）、物流（开放平台）
- **意图规则**：`human_transfer_intent`、`address_change`、关键词 DB
- **可观测**：`core/ops_telemetry`（intent、rewrite、recall、turn 记录）
- **RAG 优化（近期）**：5s 超时跳过检索；`ai_max_tokens=500`

**仍偏「LLM 自由发挥」的部分：**

- Agno Agent 仍 **`search_knowledge=True`**，通用问答几乎每轮走 RAG
- `TaskState.intent` 主要靠 `_guess_intent` 关键词，**未驱动全局 stage 跳转**
- 各 Handler 各自为政，**没有统一的 SessionMemory / StateMachine 中枢**
- 情感分析（`BuyerEmotionHandler`）仍参与链路，与 V4「情感仅记录、不参与决策」理念有差距

## 3. V4 五模块逐项对照

### 3.1 SessionMemory → 可升级为「会话中枢」

**V4 做法：** `intent + slots + stage` 单一对象，Redis 持久化，每次更新可观测。

**当前项目：**

```python
# Agent/CustomerAgent/conversation_memory.py
@dataclass
class TaskState:
    intent: str = "general"
    slots: Dict[str, str] = {}
    pending_confirm: List[str] = []
    flow_node: str = "general"
```

已持久化到 `chat_sessions.memory` / `task_state_json`，与 V4 的 SessionMemory **高度同构**，缺的是：

- 统一的 **`stage`** 命名规范（当前是 `flow_node`，语义接近但不统一）
- **跨 Handler 读写**同一状态对象（改址填的 slots，AI 回复时应可见）
- 可选 **Redis**（当前 SQLite 够用；多实例部署时再考虑）

**借鉴建议：** 不必新建一套 SessionMemory，可将 `TaskState` 升格为「会话唯一真相源」，各 Handler 只读写 slots/stage，不各自维护隐式状态。

#### 3.1.1 统一写入：`update_session_state`（时机与并发）

「各 Handler 成功解析后写 slots」方向正确，但需避免 **分散写入 + 并发覆盖**：

- **写入时机：** 仅在 Handler `handle()` **成功返回** 后更新；失败不污染状态。
- **并发安全：** 所有写操作发生在 `MessageConsumer` 的 **per-buyer 锁内**（项目已有 `BuyerLockRegistry`，同买家串行，天然安全）。
- **单一入口：** 禁止各 Handler 直接改 `task_state_json`，统一经：

```python
def update_session_state(
    session_id: int,
    *,
    intent: str | None = None,
    slots: dict | None = None,      # 增量 merge，非全量覆盖
    stage: str | None = None,
    last_intent: str | None = None,  # 供追问延续 RAG 判定
) -> TaskState:
    """读-改-写 SQLite，slots 做 dict.update，避免后写覆盖先写。"""
```

- **merge 而非 replace：** 改址写入 `phone/address`，售后写入 `order_sn`，互不抹掉对方字段。
- **可观测：** 每次 `update_session_state` 打 debug 日志或写入 `ops_telemetry`（stage、slots keys、触发 Handler 名）。

### 3.2 StateMachine → Handler 链的「上层编排」

**V4 做法：** 规则决定 `start → collect_info → recommend → quote → end`，零 Token。

**当前项目：** 更接近 **「扁平责任链 + 专用子流程」**：

| 场景 | 当前机制 | 是否类状态机 |
|------|----------|-------------|
| 改址 | `AddressChangeHandler` + 地址解析 + 弹窗 | 是（隐式） |
| 售后 | `AfterSalesApplyHandler` + 订单窗口策略 | 是（隐式） |
| 物流 | `OrderLogisticsHandler` + 开放平台 | 是（单次） |
| 转人工 | `KeywordHandler` + `has_explicit_transfer_intent` | 规则，零 LLM |
| 通用问答 | 直接进 `AIReplyHandler` | **LLM 自由发挥** |

**差距：** 缺少「**全局 stage**」——例如买家在改址流程中又问商品，系统不知道应继续 collect_info 还是切到 product。

**借鉴建议（电商版 stage 示例）：**

```
idle → address_change → after_sales → logistics → product_qa → human → idle
```

- 用 **规则 + 当前 slots** 决定下一 stage，而非每轮 LLM 分析阶段

#### 3.2.1 stage 与 Handler 链的协作（推荐：阶段隔离，不改链顺序）

**不推荐：** StateMachine 在链外「先选 Handler再执行」——会破坏现有 **先命中先处理** 的优先级（例如改址必须在 AI 之前）。

**推荐：** **保持链顺序不变**，在每个 Handler 的 `can_handle()` 内增加 **stage 门禁**：

```python
# BaseHandler 或各 Handler 共用
def _stage_allows(self, handler_stage: str, current_stage: str) -> bool:
    if current_stage == "idle":
        return True  # 空闲：按原顺序尝试所有 Handler
    return current_stage == handler_stage  # 非 idle：仅专属 Handler 可处理


# AddressChangeHandler.can_handle
def can_handle(self, context):
    if not self._stage_allows("address_change", get_current_stage(context)):
        return False
    return is_address_change_intent(text) or current_stage == "address_change"
```

| 当前 stage | 行为 |
|------------|------|
| `idle` | 按原链顺序：改址 → 物流 → 售后 → … → AI |
| `address_change` | **仅** AddressChangeHandler 可处理；其余 Handler `can_handle=False` |
| `after_sales` | **仅** AfterSalesApplyHandler |
| `product_qa` | 跳过业务 Handler，进入 AI（+ 按需 RAG） |

**stage 切换：** Handler 成功处理或用户意图明确切换时，调用 `update_session_state(stage=...)`；`StateMachine.transition()` 可作为 **纯函数** 供 Handler 或 AI 入口调用，**不替代**责任链。

这样既保留链的灵活性与优先级，又实现 **阶段隔离**，改动面小于「链外编排」。

### 3.3 PromptBuilder → 已有，需「硬上限」

**V4 做法：** 系统角色 + 阶段指示 + ≤5 轮历史 + ≤3 条文档 + 当前输入。

**当前项目 `build_layered_prompt`：**

- 长期摘要 + 任务状态 + 短期原文（可配置 6–12 轮）+ 本轮买家消息
- 未回复合并：最多 3 条、2000 字符
- 时间戳已改为 ISO 完整格式

**差距：**

- 短期记忆轮数上限（6–12）仍可能偏长
- RAG 结果条数由 Agno 内部控制，**未在 PromptBuilder 层显式 cap**
- 缺少「**当前 stage 指示**」独立段落（V4 的核心降 Token 手段）

**借鉴建议：**

- 短期记忆：**硬限制 5 轮**（与 V4 对齐）
- RAG：**最多 3 条**写入 prompt
- 增加固定块：`【当前流程】stage=after_sales, slots={order_sn: ...}`

### 3.4 按需向量检索 → **最高优先级借鉴点**

**V4 做法：** 仅 `recommend / quote` 阶段 `need_retrieval=True`，减少 60%+ 检索。

**当前项目：**

```python
# Agent/CustomerAgent/agent.py
search_knowledge=True  # Agno 每轮可能触发 knowledge_retriever
```

即：打招呼、催发货、改址引导等 **不需要知识库** 的场景，仍可能触发 LanceDB 检索（虽有 5s 超时，但仍有调用成本与延迟）。

**电商场景下的「按需检索」映射：**

| 用户输入类型 | 是否 RAG | 替代手段 |
|-------------|---------|---------|
| 你好 / 在吗 | ❌ | 固定寒暄或短 LLM |
| 改址 / 物流 / 售后 | ❌ | 已有 Handler + API |
| 转人工 | ❌ | Keyword / 规则 |
| 商品价格 / 规格 / 有没有 XX 款 | ✅ | RAG + `get_shop_products` |
| 知识库外泛问 | ✅（或仅 LLM） | 兜底话术 |

**借鉴建议（初版）：**

```python
def need_retrieval(intent: str, stage: str) -> bool:
    return intent in ("product_spec", "price", "general_product") \
        and stage in ("product_qa", "recommend")
```

在调用 Agent 前判断；为 False 时设置 `search_knowledge=False` 或跳过 retriever——这与 V4 收益模型一致，**预计 Token + 延迟双降**。

#### 3.4.1 按需 RAG 判断条件（细化版）

初版仅看 `intent + stage` 不够，建议 **四维度** 联合判定：

| 维度 | 说明 | 示例 |
|------|------|------|
| **intent + stage** | 商品/价格类意图且处于商品问答阶段 | 问规格、问多少钱 |
| **Handler 已处理** | 本轮消息已被业务 Handler 消费 → **硬禁止 RAG** | AddressChange / AfterSales / OrderLogistics 返回 `True` |
| **追问延续** | 用户在同一会话追问同一主题 → **仍应 RAG** | 先问「价格」→ 再问「那运费呢」 |
| **显式否定** | 寒暄、转人工、纯流程引导 | 永远不走 RAG |

**推荐伪代码：**

```python
def need_retrieval(
    *,
    intent: str,
    stage: str,
    handler_already_processed: bool,
    last_intent: str | None,
    current_text: str,
) -> bool:
    # 1. 业务 Handler 已处理：禁止 RAG（与 AI 路径互斥）
    if handler_already_processed:
        return False

    # 2. 非商品类意图 / 非商品阶段：不检索
    product_intents = {"product_spec", "price", "general_product"}
    product_stages = {"product_qa", "recommend"}
    if intent not in product_intents and stage not in product_stages:
        # 3. 追问延续：上一轮已是商品意图，本轮短追问仍检索
        if not _is_follow_up_product_question(last_intent, current_text):
            return False

    # 4. 寒暄 / 流程类：不检索
    if intent in ("chat", "greeting") or stage in ("idle", "address_change", "after_sales", "logistics"):
        return False

    return True


def _is_follow_up_product_question(last_intent: str | None, text: str) -> bool:
    """例如：上轮 price，本轮「那运费呢」「包邮吗」仍视为商品追问。"""
    if last_intent not in ("product_spec", "price", "general_product"):
        return False
    follow_up_markers = ("运费", "包邮", "多少钱", "价格", "贵不贵", "有货", "规格", "颜色")
    return any(m in text for m in follow_up_markers)
```

**`last_intent` 来源：** 写入 `TaskState.intent`（或 `chat_sessions.task_state_json`），每轮 AI/规则路径结束后更新；`build_layered_prompt` 的短期记忆仅作辅助，**以 TaskState 为准**。

**与 Consumer 协作：** `handler_already_processed` 由 `_process_message` 在链执行结束后传入 AI 入口（`metadata["handled_by"]` 或 `processed=True` 且 handler 非 AI/CatchAll）。

### 3.5 零 Token 规则节点 → 项目强项，可扩展

**V4 做法：** 手机号、姓名、预算、日期等用正则抽 slot。

**当前项目已有：**

| 模块 | 规则能力 |
|------|----------|
| `utils/address_parse.py` | 手机、姓名、省市区 |
| `utils/after_sales_policy.py` | 售后意图枚举 |
| `utils/human_transfer_intent.py` | 转人工 / 找经理 |
| `Message/handlers/ai_handler._guess_intent` | 物流/售后/价格等关键词 |
| `KeywordDetectionHandler` | DB 关键词 |

**差距：** slot 抽取 **分散在各 Handler**，未回写统一 `TaskState.slots`；AI 路径仍可能让 LLM「重新理解」已抽取的信息。

**借鉴建议：** 改址/售后/订单解析成功后 **统一 `TaskState.update_slot()`**，Prompt 只读 slots，不让 LLM 从长历史里「猜」。

## 4. V4 其他概念在本项目的适用性

### 4.1 意图分类用「小模型 / Haiku」

V4：意图用 Haiku，回复用 Sonnet。

Customer-Agent：意图多为 **规则**；通用意图 `_guess_intent` 也是关键词。

**建议：** 仅当规则置信度低时，再调 **轻量 LLM 做 intent 分类**（可选，非必须）。拼多多口语、错别字多，规则 + 现有 `human_transfer_intent` 已覆盖大部分。

### 4.2 情感分析简化

V4：情感仅记录标签，不参与流程。

当前：`BuyerEmotionHandler` 达阈值可转人工。

**建议（两层，互不混用）：**

| 层级 | 行为 | 是否参与 stage |
|------|------|----------------|
| **记录** | 情感标签写入 telemetry / 会话备注 | ❌ 不参与 stage 跳转 |
| **阈值动作** | 评分低于阈值（如愤怒 `score ≤ -0.6` 或连续 N 次负面）→ **直接触发转人工工作流** | ❌ 不走 StateMachine 规则 |

```python
# 伪代码：简单可靠，与 stage 解耦
if emotion_score <= ANGER_THRESHOLD:
    await escalate_to_human(reason="buyer_emotion_critical")
    return True  # 不再进入 AI / RAG
elif emotion_score <= WARN_THRESHOLD:
    emit_human_assist_warning(...)  # 仅预警弹窗，不阻断 AI
```

- **愤怒等极端情绪：** 硬阈值 → 转人工（类似 V4「不参与策略选择」，但是 **独立硬规则**）
- **一般负面：** 仅预警，不修改 `stage`，不禁止 RAG
- 与 V4 一致：**情感不写入 `StateMachine.transition()`**，避免不可预测分支

### 4.3 MCP 企业集成

V4 用 MCP 连订单/库存/CRM。

当前：拼多多 **HTTP API + Agent Tools**（`get_shop_products`、`send_goods_link`、MMS 改址等）。

**结论：** 能力等价，**无需为了 V4 引入 MCP**；若未来多平台统一，可再评估 MCP 作为工具层协议。

### 4.4 Redis 三级缓存

V4 V3 有 Redis；当前项目 SQLite + 内存 Hub + 可选 LanceDB。

**结论：** 单店桌面部署 **SQLite 足够**；多 worker / 多机再考虑 Redis 存 SessionMemory。

## 5. 推荐演进路线（讨论用，非实施承诺）

### Phase 0：保持现状 + 小优化（低成本）

- [x] RAG 超时跳过（已做）
- [x] Token / 并发配置（已做）
- [ ] 短期记忆硬 cap 5 轮、RAG 结果 cap 3 条（配置级）
- [ ] ops_telemetry 面板展示 stage / slots / 是否触发 RAG

### Phase 1：按需 RAG（高收益，改动集中）

- 实现 **四维度** `need_retrieval()`（见 §3.4.1）：intent/stage、Handler 已处理、追问延续、显式否定
- Consumer 向 AI 入口传递 `metadata["handled_by"]` / `handler_already_processed`
- TaskState 持久化 `last_intent` 供追问判定
- 预估：检索次数 **-50%～70%**（需实测）

### Phase 2：统一 TaskState 为 SessionMemory

- 引入 **`update_session_state()`** 单一写入口（§3.1.1），slots 增量 merge
- 各 Handler 成功解析后仅通过该 API 写 slots/stage
- `build_layered_prompt` 顶部固定输出 stage + slots
- `flow_node` 重命名为 `stage`，文档化枚举值

### Phase 3：stage 阶段隔离（可选，中成本）

- 新增 `utils/session_state_machine.py`（纯规则 `transition()`，无 LLM）
- **不改 Handler 链顺序**；各 Handler `can_handle` 增加 stage 门禁（§3.2.1）
- StateMachine 只管 stage 更新与「是否允许 RAG / 是否允许 AI」

### Phase 4：多模型路由（可选，有成本）

- 意图分类 / 摘要：便宜模型
- 最终回复：主模型  
  与 V1 文章类似；当前若已用 `qwen-turbo` 单模型，收益有限。

## 6. 不建议照搬的部分

| V4 做法 | 原因 |
|---------|------|
| 完整照搬汽车试驾五阶段 | 电商流程是改址/售后/物流/商品，阶段定义不同 |
| 全面去掉 Handler 链 | 现有链已覆盖拼多多特有能力，比纯状态机更清晰 |
| 为 V4 引入 LangGraph | 当前 Agno + Handler 已够用，引入新框架成本高 |
| 向量库全量每轮写入 | 当前长期摘要已是规则版，方向正确，应坚持 **非向量** |
| 情感驱动 stage 策略 | 易不可控；极端情绪用 **硬阈值转人工**，一般情绪仅预警（§4.2） |

## 7. 与简历 / 对外叙述的关系

若将 V4 思路融入 Customer-Agent，可在简历中表述为：

> 在自研拼多多 AI 客服中，采用 **Handler 责任链 + 结构化 TaskState**，并将通用对话从「每轮 RAG + LLM」优化为 **规则意图 + 按需检索 + 有上限 Prompt 构建**，降低 Token 消耗并提升流程可观测性。

这比写「用了 LangChain」更准确，也与实际代码一致。

1. **按需 RAG**：在 intent/stage 基础上，增加 Handler 已处理标志、以及 `last_intent` 追问延续判定。
