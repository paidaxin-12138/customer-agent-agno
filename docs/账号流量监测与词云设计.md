# 账号流量监测与周词云 — 设计说明（待实施）

> **文档性质**：产品设计 + 技术方案讨论稿，**尚未开发**。  
> **目标用户**：拼多多商家 / 运营，按**店铺客服账号**查看接待与 AI 成本。  
> **关联模块**：`OpsDashboardUI`、`ops_cost_logs`、`chat_messages`、`ops_traces`

---

## 1. 需求摘要

为每个**客服账号**提供独立监测页（顶部下拉框切换账号），展示：

| 指标 | 说明 |
|------|------|
| **Token 用度** | 该账号 AI 调用消耗的 prompt + completion tokens（及可选估算费用） |
| **访问次数 / 接待量** | 买家消息数、AI 回复数、可选活跃会话数 |
| **平均回复时间** | 从收到买家消息到发出回复的耗时（建议区分 AI 与规则 Handler） |
| **监测表** | 按日汇总，默认近 7 天 |
| **周词云** | 根据一周买家咨询原文生成词云 + Top 词列表 |

---

## 2. 与现有系统的关系

### 2.1 已有能力

| 能力 | 位置 | 按账号 |
|------|------|--------|
| Token / 成本 | `ops_cost_logs`，`core/ops_telemetry.record_llm_usage` | 部分：`session_key` 含 `shop_id`、`seller_user_id` |
| AI 链路 | `ops_traces`（问题、答案、意图） | 同上 |
| 对话原文 | `chat_messages`（`account_id`、`sender_type`） | **可直接按账号** |
| 进程级 QPS | `core/app_metrics` | 全进程，**不可**按账号 |
| 运营看板 UI | `ui/ops_dashboard/ops_dashboard_ui.py` | 全店汇总，**无账号下拉** |

### 2.2 `session_key` 格式（用于解析账号）

```
{channel}:{shop_id}:{seller_user_id}:{buyer_uid}
```

示例：`pinduoduo:722406697:174053423:5047840775`

统计 Token / trace 时可按前缀匹配：`pinduoduo:{shop_id}:{user_id}:%`

### 2.3 缺口

- **平均回复时间**：AI Handler 有 `perf_counter` 日志，**未持久化**到 DB  
- **ops 表无独立 `shop_id` / `account_id` 字段**，长期建议写入时冗余，避免解析字符串  
- **词云**：无现成 UI，需分词 + 停用词 + 渲染（如 `wordcloud`）

## 3. 页面设计（草案）

### 3.1 入口

- **推荐**：主导航新页 **「数据监测」**（面向店主，简单）  
- **可选**：在现有「后台看板」增加账号筛选（面向研发排查，信息更全）  
- 两者可共用同一套聚合逻辑 / 日 rollup 表

### 3.2 线框

```
┌─────────────────────────────────────────────────────────┐
│  数据监测                                                │

│  时间：[近7天 ▼]  [刷新]                                 │
├─────────────────────────────────────────────────────────┤
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐   │
│  │ 接待人次  │ │ AI 回复次│ │ Token 合计│ │ 均回复耗时│   │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘   │
├─────────────────────────────────────────────────────────┤
│  [折线] 每日 Token / 消息量                              │
├─────────────────────────────────────────────────────────┤
│  [表格] 日期 | 买家消息 | AI回复 | Token | 均耗时        │
├─────────────────────────────────────────────────────────┤
│  本周接待词云（买家消息）                                  │
```

### 3.3 账号下拉数据源

与「自动回复」一致：

- `db_manager.get_all_channels` → `get_shops_by_channel` → `get_accounts_by_shop`  
- 展示：`username（shop_name）`  
- 内部键：`(channel_name, shop_id, user_id)` → 解析为 `accounts.id` 用于查 `chat_messages`

## 4. 指标口径（实施前需产品确认）

### 4.1 Token 用度

- **定义**：该账号下所有 AI 调用的 `prompt_tokens + completion_tokens` 之和  
- **来源**：`ops_cost_logs`，`session_key` 前缀匹配  
- **说明**：改址 / 售后 / 关键词等规则 Handler **不占 Token**（与 Phase 1 按需 RAG 一致，可在页面上单独展示「规则处理占比」）  
- **可选展示**：Prompt/Completion 拆分、估算 `cost_usd`、RAG 命中占比（`cache_hit` 或 trace 中 `recall_json` 非空）

### 4.2 访问次数（接待量）

建议 UI 展示多个数字，避免单一「访问次数」歧义：

| 指标 | 定义 | 来源 |
|------|------|------|
| 买家消息数 | `sender_type=customer` 条数 | `chat_messages` + `account_id` + 时间 |
| AI 回复数 | `sender_type=ai` 条数 | 同上 |
| 活跃会话数（可选） | 去重 `session_id` 或 buyer_uid | `chat_sessions` / `session_key` |

**待确认默认值**：主卡片展示「买家消息数」还是「活跃买家数」。

### 4.3 平均回复时间

**方案 A（推荐，准确）** — 新埋点  

- 起点：Consumer 收到消息或 AI Handler 开始处理  
- 终点：出站 `send_text_to_buyer` 成功  
- 写入：扩展 `ops_traces` 或新表 `ops_turn_metrics` 字段 `latency_ms`、`handler_name`  
- 平均：可拆 **AI 路径** vs **规则 Handler**

**方案 B（零埋点，凑合）** — 消息时间差  

- 同 session：下一条 `ai/human` 的 `created_at` − 上一条 `customer` 的 `created_at`  
- 缺点：合并消息、排队降级、watchdog 会拉高；多 Handler 混在一起  

**建议**：一期可用 B 验证页面；二期用 A 校准。

### 4.4 时间范围

- 默认：**近 7 滚动天** 或 **自然周（周一 0:00～周日 23:59）**  
- 监测表与词云**共用同一时间范围**  

**待确认**：默认用哪一种。

## 5. 周词云设计

### 5.1 文本来源

**优先**：`chat_messages WHERE sender_type='customer' AND account_id=? AND created_at IN range`

**可选**：`ops_traces.query_text`（可能与 chat_messages 重复，需去重或只选一种）

**待确认**：词云仅买家原文，还是包含 AI 回复。

### 5.2 预处理

1. 过滤过短文本（单字「嗯/好/在吗」）  
2. 排除平台系统句、文明用语模板（可参考 `utils/platform_system_msg`）  
3. 中文分词：`jieba`（可选词性过滤）  
4. 停用词：「亲、呢、哦、请问、一下、吗、的」+ 可配置店铺词表  

### 5.3 展示（PyQt6）

| 方案 | 说明 |
|------|------|
| `wordcloud` → PNG → `QLabel` | 视觉效果好，多一个依赖 |
| Top30 词表 + 字号/进度条 | 零依赖，可点击查会话 |
| **推荐** | 词云图 + Top 词列表并存 |

### 5.4 周期

与监测表一致；可缓存周词云 JSON/PNG 路径，避免每次打开重算。

## 6. 数据层建议

### 6.1 第一版（MVP）

- 不建新表，实时 SQL 聚合：  
  - `chat_messages` 按 `account_id` + 日期 GROUP BY  
  - `ops_cost_logs` 按 `session_key` LIKE 前缀 + 日期 GROUP BY  
- 词云：按周查询 buyer 文本，内存分词生成  

### 6.2 第二版（规模化）

**日汇总表 `account_daily_stats`（建议字段）**：

```
account_id, stat_date,
buyer_msg_count, ai_reply_count, session_count,
prompt_tokens, completion_tokens,
avg_reply_ms, p95_reply_ms,
rag_call_count, handler_only_count
```

- 写入：每日凌晨 batch，或 AI 回复成功后增量更新（可挂 `core/production_services`）  
- 词云：仍按周查原文，或异步写 `wordcloud_cache`

### 6.3 ops 表扩展（长期）

在 `ops_cost_logs`、`ops_traces` 增加：

- `shop_id` (String)  
- `account_user_id` (String，商家客服 UID)  
- `account_id` (Integer，可选，FK accounts.id)  
- `latency_ms` (Integer，可选)  

写入点：`finish_turn` / `record_llm_usage` / Consumer 成功出站处，从 `metadata` 注入。

## 7. 隐私与合规

- 监测页、词云、导出**不得**展示 Cookie、完整手机号  
- 买家 uid 展示可脱敏  
- 对话导出与 `utils/log_redact` 策略一致  
- 桌面端单用户场景，账号下拉即数据边界

## 8. 实施阶段与工作量估算

| 阶段 | 内容 | 开发量级（参考） |
|------|------|------------------|
| **P0 MVP** | 账号下拉 + 7 日 Token/消息数/AI 次数 + 按日表格 | 约 2～3 人日 |
| **P1** | 折线图 + 周词云 + Top 词 | +2～3 人日 |
| **P2** | 回复耗时埋点 + 均耗时/P95 | +2～3 人日 |
| **P3** | 日 rollup、导出 CSV/PDF 周报 | +2～3 人日 |

**难度评估**：整体 **中等偏易**；唯一偏难项为**精确平均回复时间**（需埋点）。Token、消息量、词云均有现成数据基础。
