# Customer-Agent 面试题与参考答案

> 基于本项目真实实现整理，适用于简历项目「拼多多 AI 客服桌面端」的面试准备。  
> 建议：先背要点，面试时用「背景 → 方案 → 权衡 → 结果」展开。

---

## 一、项目概述

### Q1. 用 1 分钟介绍这个项目

**答：**  
Customer-Agent 是面向拼多多商家的 **AI 客服桌面应用**（PyQt6）。买家消息经 **WebSocket** 进入系统，经 **消息队列 + Consumer** 异步处理，再走 **Handler 责任链**（改址、物流、售后、关键词转人工、AI 回复等），最后通过 MMS HTTP 接口发回买家。  
AI 侧用 **Agno + OpenAI 兼容 LLM**，知识库用 **LanceDB**；会话与关键词等存在 **SQLite**。  
核心工作包括：消息链路与 Handler 设计、按需 RAG 优化、SessionMemory（TaskState）、stage 阶段隔离、Cookie/登录链路问题排查，以及生产健康检查与部署相关改造。

---

### Q2. 为什么用桌面端而不是纯 Web / 纯后端？

**答：**

| 原因 | 说明 |
|------|------|
| Cookie 与登录 | 拼多多商家后台依赖 **Playwright 扫码/密码登录**，Cookie 存在本地；桌面端更贴近店主使用习惯 |
| 实时性 | WebSocket 长连接 + 本地 UI 弹窗（人工协助、改址确认） |
| 数据本地化 | SQLite、LanceDB、日志在本机，适合单店/少量店铺部署 |
| 开放平台可选 | 物流等可走 `pinduoduo_open` HTTP API，但主链路仍是 MMS Cookie |

纯后端需要额外解决 Cookie 同步、Playwright 远程化、UI 人工协同等问题，成本高。

---

### Q3. 一条买家消息从进来到回复的完整链路？

**答：**

```
买家消息 (拼多多 WS)
  → PDDChannel 解析为 Context，入队 MessageWrapper
  → MessageConsumer（per-buyer 锁串行）
  → prime_session_stage_on_context（读 TaskState.stage）
  → Handler 链顺序尝试 can_handle → handle，首个 success 即 break
  → 出站统一 channel_send.send_text_to_buyer
  → 若全链未处理 → fallback_reply 安抚
```

AI 路径额外步骤：合并未回复买家消息 → `build_layered_prompt` → `need_retrieval` 决定是否 RAG → Agno `arun` → 持久化 `persist_turn_memory`。

**关键文件：** `Channel/pinduoduo/pdd_chnnel.py`、`Message/core/consumer.py`、`Message/handler_chain_factory.py`

## 二、架构与责任链

### Q4. Handler 链顺序为什么这样？改顺序会怎样？

**答：**  
当前顺序（`Message/handler_chain_factory.py`）：

```
AddressChange → OrderLogistics → ImageVideo → AfterSales
→ BuyerEmotion → Keyword → AIReply → CatchAll
```

**原因：**

- **改址/物流/售后** 是强业务、可规则化，必须在 AI 前，避免 LLM 乱答或重复发卡
- **图片视频** 需转人工（AI 看图能力有限）
- **关键词** 命中转人工，优先级高于泛化 AI
- **CatchAll** 仅兜底

若把 AI 提前：改址意图可能被 AI 闲聊掉；若把 Keyword 放最后：转人工延迟。

---

### Q5. `can_handle` 和 `handle` 的区别？为什么命中即 break？

**答：**

- **`can_handle`**：轻量判断「我是否负责这类消息」，无副作用
- **`handle`**：真正执行业务（查 API、发话术、调 LLM）

Consumer 按顺序遍历，**第一个 `can_handle=True` 且 `handle` 返回 success 的 Handler 终止链**，保证一条消息只由一个主路径处理，避免重复回复。

---

### Q6. Phase 3 stage 门禁解决什么问题？为何不改链顺序？

**答：**  
**问题：** 买家进入改址/售后/物流流程后，仍可能被 Keyword、AI 等 Handler 抢走，打断流程。

**做法：** 在 `BaseHandler.can_handle` 里先查 `get_current_stage()`，只有 `current_stage ∈ allowed_stages` 才继续。例如：

| Handler | allowed_stages |
|---------|----------------|
| AddressChangeHandler | idle, address_change |
| AfterSalesApplyHandler | idle, after_sales |
| OrderLogisticsHandler | idle, logistics |
| AIReplyHandler | idle, product_qa, recommend |
| Keyword / 情感 / 图视频 | idle only |
| CatchAllHandler | idle only |

**不改链顺序的原因：** 链顺序表达**业务优先级**（改址永远先于 AI）；stage 表达**会话阶段**。两者正交：idle 时按原优先级；非 idle 时只允许专属 Handler。

**关键文件：** `Message/handlers/base.py`、`Agent/CustomerAgent/conversation_memory.py`（`get_current_stage`）

---

### Q7. TaskState 里 intent / slots / stage / last_intent 各干什么？

**答：**

| 字段 | 作用 |
|------|------|
| `intent` | 当前轮意图（price、logistics、after_sales…） |
| `last_intent` | 上一轮意图，供「那运费呢」类追问判定是否继续 RAG |
| `slots` | 结构化槽位（order_sn、phone、address…），Handler 写入，Prompt 只读 |
| `stage` | 会话阶段（idle、address_change、after_sales、logistics、product_qa…） |
| `pending_confirm` | 待买家确认的信息 |

持久化在 `chat_sessions.task_state_json`，是 SessionMemory 的单一真相源。

---

### Q8. 为什么 `update_session_state` 要单一写入口、slots 要 merge？

**答：**

- **单一入口**：禁止各 Handler 直接改 JSON，避免分散逻辑、难观测
- **merge 而非覆盖**：改址写 `phone/address`，售后写 `order_sn`，互不抹掉
- **时机**：仅在 Handler `handle()` **成功返回后** 写；失败不污染状态
- **并发**：写发生在 Consumer 的 **per-buyer 锁内**，同买家串行，天然安全

**关键文件：** `Agent/CustomerAgent/conversation_memory.py`

## 三、AI 与 RAG

### Q9. 如何从「几乎每轮 RAG」改成按需 RAG？判定条件？

**答：**  
实现 `utils/need_retrieval.py`，四维度：

1. **`handler_already_processed=True`** → 硬禁止（业务 Handler 已处理）
2. **寒暄/问候 intent**（greeting）→ 不检索
3. **流程 stage**（address_change、after_sales、logistics）→ 不检索
4. **商品意图**（product_spec、price、general_product）或 **product_qa/recommend stage** → 检索
5. **追问延续**：`last_intent` 已是商品类，且本轮含「运费、包邮、价格…」→ 仍检索

Consumer 设置 `metadata["handled_by"]` 和 `handler_already_processed`（非 AI/CatchAll 为 true）。

---

### Q10. `need_retrieval=False` 时 Agno 如何跳过检索？

**答：**  
Agno Agent 初始化时 `search_knowledge=True`，但在 `AIReplyHandler._call_bot_once` 调用前：

```python
rag_tok = set_knowledge_retrieval_enabled(rag_on)
try:
    await bot.async_reply(...)
finally:
    reset_knowledge_retrieval_enabled(rag_tok)
```

`Agent/CustomerAgent/agent.py` 里 `knowledge_retriever` 首行检查 `ContextVar`，为 False 直接 `return None`；同时 RAG 结果 **cap 3 条**。

---

### Q11. `build_layered_prompt` 分几层？为何 cap 5 轮 / 3 条 RAG？

**答：**  
三层 + 本轮输入：

1. **【当前流程】** stage + slots（Phase 2）
2. **长期摘要**（规则摘要，非向量）
3. **任务状态**（intent、槽位、待确认）
4. **短期记忆**（最近对话原文，**硬 cap 5 轮**）
5. **本轮买家消息**（含 ISO 时间戳）

Cap 原因：对齐 V4 PromptBuilder——控制 Token 与延迟；RAG 3 条足够 grounding，再多噪声大。

---

### Q12. AI 失败、超时、排队过长时的降级策略？

**答：**

| 场景 | 策略 |
|------|------|
| LLM 瞬时网络错误 | `chat.llm_sync_retry_enabled`，同步重试 1 次 |
| 无效/占位回复 | `_handle_unknown_ai_failure`，发配置兜底话术 |
| 明确转人工意图 | `has_explicit_transfer_intent` → 立即转人工 |
| 排队过长 | `should_queue_degrade()` → 降级话术 + 可选人工弹窗 |
| 入站 watchdog | 超时未回复 → 转人工/安抚 |
| 全链未处理 | `fallback_reply` |

RAG：`knowledge_retrieval_timeout_sec`（默认 5s）超时跳过检索，不阻塞主链路。

---

### Q13. 「产品经理」兜底为什么要单独 escalation？

**答：**  
AI 有时会输出「已反馈产品经理」类话术，业务上需要**人工跟进**而非让买家干等。  
`should_escalate_ai_pm_reply` 检测回复内容 → `emit_human_assist` 弹窗 + 摘要，与关键词转人工共用 `core/human_assist_bus.py`，但触发条件不同（内容检测 vs 关键词）。

## 四、拼多多渠道与工程细节

### Q14. WebSocket 和 HTTP Cookie 分别用在哪？

**答：**

| 通道 | 用途 |
|------|------|
| **WebSocket** | 实时收买家消息、auth、心跳；`PDDChannel` 维护连接与重连 |
| **HTTP + Cookie** | 发消息、查单、改址、售后卡片、set_csstatus 在线状态、getToken 等 MMS API |
| **开放平台**（可选） | `pdd.logistics.ordertrace.get` 等，用 client_id/secret/token |

---

### Q15. Cookie 过期怎么处理？「登录成功但提示缺 Cookie」根因？

**答：**  

**过期：** `Channel/pinduoduo/utils/base_request.py` 检测 `error_code=43001` +「会话已过期」→ 优先 `refresh_pdd_cookies`，失败再 `login_pdd` 全量登录 → 更新 DB → 重试请求。

**误报根因（真实 bug）：** Playwright 登录成功且 DB 有 Cookie（`has_cookies=True`），但 `get_accounts_by_shop` **列表接口不返回 cookies**（安全设计）。自动回复页点「上线」时直接用内存里 `account_data["cookies"]`（恒为 None）→ 报「缺少 cookies」。

**修复：** `ui/auto_reply_ui.py` 中 `resolve_account_secrets()` 操作前 `get_account(..., include_secrets=True)` 拉完整凭据；重复添加账号时 `user_ui.py` 会更新 Cookie 而非忽略。

---

### Q16. Playwright 登录与 BaseRequest 如何配合？

**答：**  
`Channel/pinduoduo/pdd_login.py`：Playwright 打开 MMS → 扫码/密码 → 导出 Cookie JSON + **同一 UA** 嵌入 Cookie（避免 UA 不一致被风控）。  
`login_pdd` 成功后写 DB；HTTP 请求用 `BaseRequest.update_cookies`；过期走 refresh/relogin 闭环。

---

### Q17. per-buyer 锁为什么需要？

**答：**  
同买家可能连发多条消息；Consumer 多 worker 并发。无锁时：

- 两条消息并行改 `TaskState` → 后写覆盖
- 可能触发两次 AI 回复
- Handler 链与 stage 更新乱序

`utils/buyer_lock_registry.py` 按 `channel_from_uid` 串行处理同一买家。

---

### Q18. 文明用语系统消息为何不能让 AI 误回复？

**答：**  
拼多多会推平台「文明用语」类系统提示。若当普通买家消息处理，AI 会对系统话回复「您好」。  
做法：`pdd_chnnel` 标记 civility → DB 存 `sender_type=system` → `AIReplyHandler._resolve_effective_buyer_query` 跳过该条，合并**真正未回复的买家消息**再进 AI。

## 五、数据与生产

### Q19. SQLite 核心表与 task_state 关联？

**答：**  
渠道 `channels` → 店铺 `shops` → 账号 `accounts`（含 cookies/password 可加密）→ 会话 `chat_sessions`（含 `task_state_json`、`long_term_summary`、`memory_summary_through_id`）→ 消息 `chat_messages`。  
`resolve_session_id` 用 channel + shop_id + user_id + buyer_uid 定位 active 会话。

---

### Q20. 为什么需要 schema migration？

**答：**  
桌面应用长期运行，用户 DB 不能删库重建。用 **Alembic** + `database/schema_migrations.py` 做 additive migration（新列、新表），启动时校验/升级，保证老用户升级后仍能跑。

---

### Q21. `/health` 和 `/ready` 区别？

**答：**

| 端点 | 含义 |
|------|------|
| **`/health`** | Liveness：进程活着就 200 |
| **`/ready`** | Readiness：至少一个店铺 WS 已连接 + 对应 `pdd_{shop_id}` Consumer 在跑 |

Docker/K8s/PM2：health 探活；ready 判断是否真正「能接消息」。详见 `docs/生产部署说明.md`。

---

### Q22. 敏感信息与日志脱敏？

**答：**  
Cookie/密码经 `utils/credential_crypto.py` 可选加密存 SQLite；列表接口 `get_accounts_by_shop` 不返回 secrets，只给 `has_cookies`。  
`utils/log_redact.py` 对 cookie、token 等键脱敏；请求日志用 `base_request._log_request` 脱敏参数。

## 六、场景题

### Q23. 改址流程中买家问「这个多少钱」会怎样？理想行为？

**答：**  
**当前（Phase 3）：** stage=`address_change` 时，仅 `AddressChangeHandler` 可通过门禁；AI 的 `can_handle` 为 False，**不会**回答价格。

**理想演进：** 可引入 `StateMachine.transition`：识别明确切到 `product_qa` 的意图时更新 stage，再放开 AI；或改址 Handler 内短答「改址进行中，价格稍后为您查」。

---

### Q24. LanceDB 检索 5s 超时，用户体验？

**答：**  
retriever 超时返回 None，Agent **无 RAG 上下文**继续生成；可能更依赖 `get_shop_products` 工具或通用话术。用户感知是回复略慢最多 5s，不会无限卡死；日志有 `knowledge_retriever 超时，跳过 RAG`。

---

### Q25. 三店同时在线，Consumer worker 怎么配？瓶颈？

**答：**  
每店铺一个 Consumer 队列 `pdd_{shop_id}`，`message_consumer_max_concurrent`（如 16～28）。瓶颈通常在：**LLM 延迟**（AI 路径）、**单 buyer 锁串行**、**Playwright/HTTP 重登录**。WS 连接数本身不是主瓶颈。

---

### Q26. 关键词热更新如何不重启？

**答：**  
`KeywordDetectionHandler` 用 COW（copy-on-write）快照 `_keywords_snapshot`；UI 改 DB 后通过 `Message/keyword_reload.py` 触发处理器 reload，新消息读新快照，旧 inflight 仍用旧快照，无全局锁长时间阻塞。

## 七、手写/设计题参考答案

### Q27. 伪代码：`need_retrieval`

```python
def need_retrieval(intent, stage, handler_already_processed, last_intent, text):
    if handler_already_processed:
        return False
    if intent in ("greeting", "chat"):
        return False
    if stage in ("address_change", "after_sales", "logistics"):
        return False
    if intent in ("price", "product_spec", "general_product"):
        return True
    if stage in ("product_qa", "recommend"):
        return True
    if last_intent in PRODUCT and any(m in text for m in FOLLOW_UP_MARKERS):
        return True
    return False
```

---

### Q28. 伪代码：Consumer 设置 `handler_already_processed`

```python
AI_HANDLERS = {"AIReplyHandler", "CatchAllHandler"}
for handler in handlers:
    if handler.can_handle(context):
        if await handler.handle(context, metadata):
            hname = handler.__class__.__name__
            metadata["handled_by"] = hname
            metadata["handler_already_processed"] = hname not in AI_HANDLERS
            break
```

### Q29. 加「抖音渠道」最小改动？

**答：**

1. `bridge/context.py`：`ChannelType.DOUYIN`
2. 新 `Channel/douyin/`：WS/HTTP 适配，解析为统一 `Context`
3. `Message/handler_chain_factory.py`：按渠道注册或复用 Handler（改址逻辑可能不同）
4. `database/db_manager.py` 账号表已按 channel 隔离
5. UI：账号管理、自动回复入口复用
6. **不必**改 Agno/Consumer 核心，只要 Context 与 outbound send 统一

## 八、三个 2 分钟故事（面试收尾用）

### 故事 1：按需 RAG

- **问题：** 每轮 LanceDB 检索，延迟 + Token 高
- **方案：** 四维度 `need_retrieval` + ContextVar 短路 retriever + 5 轮/3 条 cap
- **结果：** 寒暄/改址/售后不走 RAG；商品与追问仍检索；可观测 `handled_by`

### 故事 2：Stage 阶段隔离

- **问题：** 改址中被 AI 抢答
- **方案：** `allowed_stages` + `prime_session_stage_on_context`，不改链顺序
- **结果：** address_change 阶段只有改址 Handler 能处理

### 故事 3：Cookie 误报

- **现象：** 登录成功，上线报缺 Cookie
- **根因：** 列表 API 不返 secrets，UI 未二次读库
- **修复：** `resolve_account_secrets`；重复添加账号时更新 Cookie
